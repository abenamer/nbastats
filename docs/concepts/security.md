# Assumptions

* The application runs on one computer for one user. It has no accounts and no authentication.
* The dashboard port binds to `127.0.0.1` by default, in the compose file (`APP_HOST_BIND`) and in the application (`APP_BIND`, for a native run); the image sets the container's own address. The database port is not published.
* The browser that opens the dashboard also opens other websites. Those websites must not be able to use the API.

# Threats and controls

| Threat | Control |
|--------|---------|
| A website you visit sends requests to `http://localhost:3000` (cross-site request forgery) | The request guard rejects state-changing requests that the browser marks as cross-site (`Sec-Fetch-Site`) or whose `Origin` differs from the `Host`, and every request the browser marks as cross-site (or same-site, another local port) to an API path, whatever its method or mode, since no link from another site legitimately points at a JSON endpoint and some reads cost a request to a paid or third-party service. On the pages and the assets a cross-site read is refused unless it is a navigation to a document (`Sec-Fetch-Mode: navigate` with `Sec-Fetch-Dest` absent or `document`), so an image, a script, a fetch or a hidden frame on another page is refused and a link from another site to a page here stays open. Same-origin reads stay open; the guard's own answers carry the security headers. Scripts without browser headers (curl) are not affected. |
| A website uses a host name that resolves to your computer (DNS rebinding) | The `Host` header must match `ALLOWED_HOSTS` (default: localhost, 127.0.0.1, [::1]). Other names get status 421. |
| Script injection through stored names (job names, franchise labels, CSV codes) | Askama escapes template output. The page scripts escape every string before it enters HTML. The Content-Security-Policy allows scripts from the application origin only. |
| SQL injection | Every value is a bound parameter. Only constant column lists and table names are formatted into SQL. |
| Decompression bomb in an uploaded gzip file | Decompression stops at 512 MB and the upload is rejected. The request body limit is 64 MB. |
| Oversized or endless download from the data source | The download stops at 256 MB; the connection has a 5-minute timeout. The source URL is configuration, not user input, and a failed download is reported to the client in fixed words, with the detail in the log. |
| CPU exhaustion through simulation parameters | Each job has an iteration limit (`MAX_ITERATIONS`) and an estimated work budget (`MAX_WORK_UNITS`). Parameters outside the limits return status 400 before a job is created. One season check needs the data: a what-if that bars too many teams of a conference fails the job before its first simulated season. The backward reading of a title record (`GET /api/strength`) runs its exact brackets on a blocking thread, one reading at a time (a second answers 429), over a window of at most 40 seasons. The return-from-absence report (`GET /api/research/return-curve`) reads a season's box-score lines once and keeps the result until the next import or sync, covers at most 80 seasons, and runs one report at a time (a second answers 429). |
| Credential leakage | The database password and the BALLDONTLIE, OpenRouter and Odds API keys are read from the environment. The password is masked in logs and on the Data page; the keys are never logged or returned by the API, and the `Debug` output of the configuration and of every adapter that holds a key redacts it. The OpenRouter key the application mints for itself (see the next row) lives in the model's memory only, and the rotation's status carries times and counts, no key and no hash. The Odds API takes its key in the request's query string, so the adapter drops the URL from a transport error before it is logged and redacts the key in `Debug` output. `.env` is excluded from version control and from the image. |
| Spending through the OpenRouter management key | `OPENROUTER_MANAGEMENT_KEY` can mint keys that spend the account. It is read from the environment, redacted in `Debug` output, never logged or returned, and sent to `OPENROUTER_BASE_URL` only, with no redirect followed. The application mints a key at start, on its schedule and on a refused question, at most once per ten minutes, each with `OPENROUTER_KEY_LIMIT` credits when it is set, and deletes only keys named with its own prefix (`OPENROUTER_KEY_NAME`) and a space; a refused question (403, the service's moderation) mints nothing, only a refused key (401) does; a leaked minted key is bounded by its limit and by the hours to the next rotation ([ADR 0015](/decisions/0015-mint-and-rotate-the-question-box-key-from-a-management-key.md)). |
| Data sent to a third party by the question box | The question, the system prompt and the tool results go to OpenRouter and the model's provider. The data is public basketball data from the sources: team results and ratings, player names, positions, box-score figures and injury statuses with the start of a description. The application stores no data about the user. The box is off until `OPENROUTER_API_KEY` or a management key is set, and the panel says what leaves the computer. |
| Prompt injection through a question or a tool result | The model has read-only tools and no SQL; it cannot change data. The use case decides what runs: tool names and arguments are checked, unknown tools and bad arguments return an error object. An answer without a lookup that returned data from the store is replaced by a fixed refusal, so a question cannot make the model answer with no data read; after a lookup, the prompt holds the model to the tool results and the lookup list shows what it read. |
| Cost or time exhaustion through the question box | One question is at most 6 model calls, 10 tool calls (calls past the budget are dropped), 700 answer tokens per call and 75 seconds; a tool result is cut at 16,000 characters and the results of one question at 64,000, plus a one-line note for each refused call (about 18,000 tokens; each later model call sends them again, so the results can add up to about 90,000 input tokens per question, a third more than at the earlier 48,000); the model's answer body is read up to 4 MB; at most 2 questions run at once (status 429); the question is at most 500 characters and the request body 16 KB. There is no daily budget: set a spending limit on the key at OpenRouter. |
| CPU and database load through worth what-ifs | A `worth` parameter on the Tonight page, its market and the injury card, or `worth_overrides` on a forecast, names at most sixteen players, checked before any is read; each window what-if is one read of the player's lines, then one read of the lines of every window's games together and one of their players, and one box-score table per player over at most 82 games' lines, built off the request thread as the season's table is. |
| Data sent to ESPN by the game report lookups and the market lines | One request per date to ESPN's public scoreboard feed, carrying the date only; no key, no personal data. The Tonight page's market lines read the night's date when the page loads and, with market tracking on, from a background task once when the night's date comes and once before each tip-off (a page view starts no capture and no write); one read at a time, at most once in five minutes per date (a failed read is tried again after one minute); the last capture before each game's start is stored with the model's numbers ([Market tracking](/concepts/market-tracking.md)), and a failure shows a fixed note while the detail goes to the log. The links kept are `https` links on an ESPN host only, opened in a new tab with `rel="noopener"`. One lookup runs at a time and a request fetches at most six dates within fifteen seconds; a date the feed lists games for is recorded, with or without reports, and asked again only while its games are recent. `GAME_REPORTS_ENABLED=false` makes no such requests, for reports or lines. |
| Data sent to The Odds API by the market lines | With `ODDS_API_KEY` set, one request per read to `ODDS_API_BASE_URL`, carrying the date's span, the sportsbook, the key and the application's `User-Agent`; no personal data. The title futures add one request a day from the day the schedule is stored to the last regular-season game, carrying the sportsbook and the key, one credit; a read that fails is tried again after an hour, and an answer the application cannot keep waits for the next day. The reads follow the same cache and cadence as ESPN's, and the tracking reads only on the night's date (Eastern time), once when it comes and once before each tip-off, so a game night costs about 20 of the plan's credits at three a read and a month in season 550 to 600; a page view adds a read when the five-minute cache has run out. The adapter follows no redirect, caps the answer at 4 MB, blanks the key in and cuts to 300 characters the service's error messages, and keeps the credit count from the answer's headers, which the panel shows; a failed read falls back to ESPN's scoreboard. The application warns at start when the base URL is not `https`. There is no daily budget beyond the capture rule: the plan's credits are the limit. |
| Key sent to the wrong host | The adapters follow no redirect, so the key and the conversation go to `OPENROUTER_BASE_URL` only, the Odds API key to `ODDS_API_BASE_URL` only and the BALLDONTLIE key to `BALLDONTLIE_BASE_URL` only; the application warns at start when any of the three URLs is not `https`. Provider error messages are cut to 300 characters before they reach the log. |
| Oversized or endless response from the results API | Each page stops at 8 MB; an error answer is read up to 4 KB for its message; a season stops at 200 pages; each request has a 60-second timeout. The base URL is configuration, not user input. The box-score and injury fetches have the same bounds per date and per report. |
| Data sent to BALLDONTLIE by the player sync | The key and a date, or the key alone for the team list, the player list, the rosters and the injury report. No personal data of the user leaves the computer. The data received is public player data (names, positions, lines, injury statuses). The application stores what the source sends, cut at 500 characters per description. One player sync runs at a time. `PLAYER_SYNC_ENABLED=false` stops the daily fetches; **Update Data**, the API and the commands still fetch on request. |
| Player search patterns | The name query is a bound parameter; its `%`, `_` and `\` are escaped so they match themselves. The query is cut at 80 characters and the result at 25 rows. |
| Container escape or privilege escalation | The application runs as a system user without privileges, with a read-only root file system, all capabilities dropped and `no-new-privileges`. |
| Path traversal through file names | Upload file names are reduced to safe characters and used for provenance only. Download file names are generated by the application. Backup labels accept only letters, digits, `_` and `-`. |
| Vulnerable dependencies | `cargo audit` runs in CI and before a release. |

# Headers

Every response carries `Content-Security-Policy`, `X-Content-Type-Options: nosniff`, `X-Frame-Options: DENY` and `Referrer-Policy: same-origin`.

# Residual risk

* Anyone with access to the computer, or to the port when you publish it on a network, can use the full API. If you publish the port, put a reverse proxy with authentication in front of it and set `ALLOWED_HOSTS`. [Tailscale Serve](/runbooks/tailscale.md) gives HTTPS and limits the readers to the devices of your tailnet, with the port still on loopback; it is not a login, and Tailscale Funnel, which opens the address to the internet, must not be used.
* There is no rate limit. A local process can queue many jobs; the runner executes them one at a time.
* The `/api/health` page shows table counts, the data directory and the masked database URL (the password masked in the user information and in a `password` query parameter alike).
